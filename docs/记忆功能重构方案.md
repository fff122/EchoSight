# EchoSight 记忆功能重构方案：从「扫描登记」到「家 + 最后见到」

> 版本：v1.0（2026-09-26）　范围：Android 端（桌面端暂不涉及）
> 目标：初赛提交（10.07）前完成核心改造，48 小时总决赛留家人端与扩展迭代。

---

## 一、诊断：现行方案A为什么难以落地

现行实现：说「扫描」→ 逐房间扫一圈 → 云端 VLM 列物品 → 打框快照（10–70s）→ 裁参考照片 → 写入 `memory.json`。查询时播报「记忆里，X在客厅…」。

四个根本问题（按严重程度排序）：

1. **记错了对象**。扫描登记下来的是"客厅有电视、沙发、茶几"——固定大件不需要记；真正要记的小件（遥控器、药盒、钥匙）恰恰扫不全、认不准。
2. **数据结构性地过期**。`ItemRec` 把「固定的家」和「最后见到」混在一条记录里，`touch()` 在每次找到时用最新房间**覆盖**原记录——家的信息被冲掉，一条"过期记忆"被当成事实播报。对盲人用户，播报"它在客厅茶几上"而实物早已被挪走，比不播报更糟：白走一趟，信任崩塌。
3. **写入负担落在盲人身上**。扫描对看不见画面的人是几分钟的高负担动作；「记一下」要求用户每次放东西都主动记账——这个行为撑不过三天。
4. **打框快照慢且不准**。VLM 画框 10–70 秒拖垮登记收尾，框不贴合导致参考照片质量差，照片比对自然不准。

**结论**：记忆的正确形态不是"房间里有什么"的静态库存，而是"我的东西平时放在哪 + 最近在哪见过"的动态记录；写入应该零负担，播报必须诚实。

---

## 二、设计原则

| 原则 | 含义 |
|---|---|
| 写入零负担 | last_seen 完全自动；家由本人说一次、家人代录为主 |
| 记忆是先验，不是答案 | 播报永远给"一般在哪 + 最后在哪见过"，不说"它肯定在" |
| 查询分级 | 家 → 最后见到 → 没见过（转搜索），逐级降级 |
| 静默写入 | 写记忆不播报，只在查询时说出——盲人不需要额外的噪音 |
| 全本地 | 记忆、照片全部存 `filesDir/memory/`，不上云，卸载即删 |

## 三、新记忆模型

### 3.1 三张表

| 表 | 内容 | 写入者 | 生命周期 |
|---|---|---|---|
| **home（家）** | 物品 → 固定位置（房间 + 地标） | 本人一次 / 家人代录 | 长期，仅显式修改 |
| **sightings（最后见到）** | 时间 + 房间 + 画面方位 + 参考小图 | **系统自动**（搜索成功时） | 每物品保留最近 3 条 |
| **refs（参考照片）** | 物品的标准照 | 成功检测帧裁剪 / 家人拍摄 | 每物品最多 3 张 |

### 3.2 memory.json schema v2

```json
{
  "version": 2,
  "items": {
    "遥控器": {
      "home":   { "room": "客厅", "spot": "茶几", "updated": 1758800000000 },
      "sightings": [
        { "ts": 1758886400000, "room": "客厅", "pos": "左前方", "ref": "遥控器_0.jpg" },
        { "ts": 1758799000000, "room": "卧室", "pos": "正前方" }
      ]
    }
  }
}
```

**v1 → v2 迁移**（`MemoryStore.init` 读到 `version` 缺失时执行一次）：
- `source == "manual"` 的旧记录 → 转 `home`（用户自己说过的位置可信）；
- `source == "scan"` / `"find"` 的旧记录 → 转为一条 `sightings`（原 lastSeen 时间戳），`home` 置空；
- 参考照片文件名不变，沿用 `refs/`。

### 3.3 写入时机（关键改动）

| 事件 | 动作 | 是否播报 |
|---|---|---|
| 搜索中**确认找到目标**（本地 YOLO 连续 ≥2 帧命中，或 VLM 确认） | 写一条 sighting：`ts` + 当前房间申报 + 方位词 + **从本地检测框直接裁 96×96 小图**存 `refs/`（YOLO 本地框是准的，完全不走 VLM 打框） | 否（静默） |
| 说「X的家在Y」/「记一下，X的家是Y」 | 写/改 `home` | 一句确认「记住了」 |
| 家人端登记（48h 迭代） | 写 `home` + 上传标准照 | — |
| 说「忘掉X」 | 清空该物品 home + sightings + refs | 一句确认 |

方位词直接复用 `Guidance` 现成的 direction 输出；房间用用户最近一次「我在X」申报，未申报则该字段留空。

### 3.4 读取口径：查询分级话术

「X 在哪」的应答顺序（`answerWhere` 重写为三级）：

1. **有 home 且近期 sighting 与之相符**（最近一条 sighting 房间 == home 房间）：
   > 「X 一般放在客厅茶几上，今天下午两点我也在客厅见过它。」
2. **有 home，但最近 sighting 在别处**（被挪动的高价值信息）：
   > 「X 一般放在客厅茶几上，不过今天下午四点，我在卧室靠右边见过它——要不要我陪你去找？」
3. **只有 sightings，没有 home**：
   > 「我没记过它的固定位置，今天下午两点在客厅靠左边见过它。」
4. **都没有**：
   > 「我没见过X，也说不上它在哪。要现在帮你扫一圈找找吗？」→ 确认后进搜索。

「找X」的搜索流程把记忆当**先验**：
> 开场话术从现在的「记忆里它在客厅…」改为「它一般放在客厅茶几上，先去那边看看，不在的话我帮你扫一圈。」

时间一律用相对表述（「刚才能看到」「一小时前」「昨天」），不报绝对时刻。

## 四、扫描功能的处置

- **移除**：扫描的「登记」分支（打框快照、批量入库整条链路从主流程摘除）。
- **保留**：「扫一圈」作为**搜索动作**——找不到时的视觉搜索，扫到目标即走"确认找到 → 自动记 sighting"。
- 老用户说「扫描」时不再问房间名，直接回应：「好，我陪你转一圈找东西，看到目标我会告诉你。」（避免功能消失带来的困惑，也为答辩保留"我们迭代过"的现场感。）

## 六、边界与降级

- **房间未申报**：sighting 缺 room，播报自动省略房间词（「今天下午在靠左边见过它」）。
- **同音/听错物品名**：沿用现有最长别名匹配；查询未命中时提示「你说的是不是：〈已有条目〉」。
- **记录数上限**：sightings 3 条/物品、refs 3 张/物品，写入时淘汰最旧；`memory.json` 全量重写沿用现机制，体量在 KB 级。
- **时间基准**：全部取系统时钟，重启无影响；`ts` 恒存毫秒，播报层才转相对时间。
- **隐私**：记忆与裁剪小图只落 `filesDir/memory/`（应用私有目录），不上云；「忘掉X」物理删除对应文件。

## 八、演示脚本（60 秒讲完记忆闭环）

1. 请评委把遥控器从茶几挪到窗台。
2. 问「遥控器在哪」→ App：「一般放在客厅茶几上，今天下午三点我在客厅见过它。」
3. 「帮我找遥控器」→ 先验引导去茶几 → 没找到 → 自动转扫描 → 窗台找到，播报方位步数。
4. 再问「现在遥控器在哪」→「今天下午四点，在客厅正前方窗台附近。」——**刚刚那条就是系统自己记的，全程没人说过"记一下"。**

## 九、答辩 Q&A 预案

- **为什么放弃扫描登记？**「第一版我们做了逐房间扫描登记，真实测试发现盲人不可能举着手机扫全屋，而 AI 打框一次要一分钟。于是把记忆改成零负担的自动 last_seen：只在系统真正看见东西的时候记一笔。这是这轮迭代里最重要的一次用户研究。」
- **记忆错了怎么办？**「我们从不把记忆当事实播报：话术永远是'一般在哪 + 最后在哪见过'，两者冲突时如实并列，并主动提议陪你去找。错误记忆的代价被限制在'多听一句话'，而不是'白走一趟'。」
- **和 Seeing AI 的区别？**「它们是实时识物，问一次答一次；我们多了个人空间记忆——家的固定位置、最后见到的自动流水、参考照片比对专属物品。设备记得你的家。」
- **隐私？**「记忆和照片全部留在手机应用私有目录，不上云，说'忘掉'即物理删除。」

## 十、验收标准

| 项 | 标准 |
|---|---|
| 自动写入 | 每次确认找到，100% 产生 sighting，无需任何用户操作 |
| 查询响应 | 本地查询 ≤ 1 秒（纯 JSON 读取） |
| 诚实性 | 蒙眼测试 5 次查询中，0 次把过期位置播报成事实 |
| 迁移 | 旧版 memory.json 升级后旧「记一下」条目仍然可查询 |
| 隐私 | 「忘掉」后对应 JSON 条目与照片文件均不存在 |
